# Command-line reference

```text
teardown <command> [flags] [arguments]
```

Every command has `--help` with its flags and examples. The help text, the shell completion
scripts and this page all describe the same command table.

| Command | What it does |
|---|---|
| [`analyze`](#analyze) | One file: type, hashes, entropy, structure, strings, findings and risk |
| [`strings`](#strings) | The strings of a file, classified (URLs, IPs, paths, commands, secrets, ...) |
| [`hash`](#hash) | MD5, SHA-1 and SHA-256 of files, plus the PE import hash and entropy |
| [`diff`](#diff) | Compare two files: sections, imports, strings, hardening, findings, risk |
| [`disasm`](#disasm) | x86 and x86-64 instructions at an address, a file offset or the entry point |
| [`xrefs`](#xrefs) | Who calls an import: its call sites in a PE image, with the code around each |
| [`hexdump`](#hexdump) | A hex and ASCII window of the raw bytes of a file |
| [`serve`](#serve) | HTTP API and web dashboard, loopback only by default ([HTTP API](api/http.md)) |
| [`mcp`](#mcp) | MCP server on stdio for AI agents ([MCP guide](mcp.md)) |
| [`completion`](#completion) | Shell completion script for bash, zsh, fish or PowerShell |
| `version` | Version, Go version, OS and architecture (`--json` for machines) |

## Exit codes

| Code | Meaning |
|---|---|
| 0 | Success |
| 1 | The command failed (file not found, unreadable, analysis error, interrupted; for `disasm`, `xrefs` and `hexdump` also an address or offset outside the file, a file that is not x86 code, an import the file does not have) |
| 2 | Usage error: wrong flags or arguments; the message names the fix |
| 3 | `analyze --fail-on <severity>`: a finding at or above that severity exists |

## Environment

| Variable | Effect |
|---|---|
| `NO_COLOR` | Any non-empty value disables colour ([no-color.org](https://no-color.org)) |
| `TEARDOWN_ASCII` | Any non-empty value replaces unicode bars and symbols with ASCII |
| `COLUMNS` | Line width of the human output (default 100) |

Colour is on when stdout is a terminal; `--color always|never|auto` overrides it.

## analyze

```text
teardown analyze <file> [flags]
```

| Flag | Meaning |
|---|---|
| `--json` | The full report as JSON, schema `teardown.report/v1` ([reference](api/schema.md)) |
| `--md` | The report as Markdown |
| `--sarif` | The findings as SARIF 2.1.0 for code-scanning dashboards ([details](#sarif)) |
| `--html FILE` | A self-contained HTML report written to `FILE` ([details](#the-html-report)) |
| `-o, --output FILE` | Write to `FILE` instead of stdout (not with `--html`) |
| `--color WHEN` | `auto`, `always` or `never` |
| `--ascii` | ASCII bars and symbols |
| `-v, --verbose` | Show the risk arithmetic, all evidence and all limitations |
| `--width N` | Line width of the terminal output |
| `--no-code` | Leave the code behind the findings (instructions, bytes, source lines) out of the output, whatever the format |
| `--code-all` | Show every code block of each finding in full in the terminal output (`--json`, `--md` and `--html` already carry them all). Not with `--no-code` |
| `--min-string N` | Minimum string length (default 5, 1 to 4096) |
| `--max-strings N` | String items kept in the report (default 2000, up to 1,000,000) |
| `--timeout DURATION` | Give up after this long (default 1m) |
| `--fail-on SEVERITY` | Exit 3 when a finding of at least this severity exists: `info`, `low`, `medium`, `high`, `critical` |

`--json`, `--md`, `--sarif` and `--html` are mutually exclusive. The gate prints what tripped it on stderr:

```console
$ teardown analyze examples/samples/upx-like.exe --fail-on high    # medium findings only: exit 0
$ teardown analyze examples/samples/upx-like.exe --fail-on medium > /dev/null
teardown analyze: --fail-on medium: 2 finding(s) at or above medium: packing.upx (medium), structure.rwx-section (medium)
$ echo $?
3
```

[`examples/ci-gate.sh`](../examples/ci-gate.sh) and [`examples/ci-gate.ps1`](../examples/ci-gate.ps1)
wrap this for a CI job.

### The code behind a finding

Findings made from imports, strings and script settings carry the code they are about ([code evidence](code-evidence.md)).
The terminal report prints the first 3 blocks of each finding, 24 lines each, under its evidence; the flagged
line starts with `>`. This is the process-injection finding of `dropper.bin` (generated by
`go run ./examples/gensamples -dropper`; it is a harmless file that only looks like a dropper to a static
scanner), with rows cut where the lines say `…`:

```console
$ teardown analyze examples/samples/dropper.bin
…
── Findings (19)
  [HIGH]     imports.process-injection  confidence medium
      Imports cover the full process-injection chain (allocate, write, execute)
      evidence: allocate or map memory in another process: KERNEL32.dll!VirtualAllocEx
      evidence: write to another process: KERNEL32.dll!WriteProcessMemory
      evidence: start or hijack a thread there: KERNEL32.dll!CreateRemoteThread
      (+2 more evidence lines, see -v)
      code: 4 blocks
        call to KERNEL32.dll!VirtualAllocEx in .text  (.text · 0x1400010bd · x86-64)
            0x1400010bd  41 b8 a4 01 00 00        mov r8d, 0x1a4
            0x1400010c3  ff 15 ef 10 00 00        call qword ptr [rip+0x10ef]  ; KERNEL32.dll!OpenProcess
            …
            0x1400010e1  c7 44 24 20 40 00 00 00  mov dword ptr [rsp+0x20], 0x40
          > 0x1400010e9  ff 15 b1 10 00 00        call qword ptr [rip+0x10b1]  ; KERNEL32.dll!VirtualAllocEx
            0x1400010ef  48 89 44 24 50           mov qword ptr [rsp+0x50], rax
            …
            0x1400010fe  4c 8d 05 fb 1e 00 00     lea r8, [rip+0x1efb]  ; 0x140003000 in .data
        call to KERNEL32.dll!WriteProcessMemory in .text  (.text · 0x1400010e1 · x86-64)
            …
        (+1 more code block, see --code-all or --json)
        limits: x86-64 code decoded as a linear sweep (ARM64 and other instruction sets
                are not supported): data inside a code section can be read as
                instructions, and one wrong byte shifts what follows.
      limitation: API presence alone proves nothing: legitimate software (debuggers, installers,
                  security and remote-support tools, games, browsers) imports the same functions.
```

`--code-all` prints every block of a finding (up to 12 of 64 lines), `--no-code` prints none and also
removes the blocks from `--json`, `--md`, `--sarif` and `--html` (the evidence line that counts the call sites
stays, so the report still says how many there are). `-v` adds every limitation of the blocks. `--json`,
`--md` and `--html` carry all the blocks unless `--no-code` is given. Markdown shows each block as a fenced
listing; SARIF carries the flagged line of the first five blocks of each finding in the `code` property of the
result. The code never changes a severity or the score, and `--fail-on` is not affected by it.

### The HTML report

`--html report.html` writes one file that opens from disk, offline: the Aurora UI kit (styles and
scripts), the layout and report page that the web dashboard uses (a navigation rail, a top bar, section
tabs as `#fragment` links and a status bar), and the report itself as an inert JSON island.
It makes no network request, and a Content-Security-Policy `<meta>` tag forbids any. With scripting
disabled the page falls back to a plain readable summary. Hostile file names and strings cannot
break out of the island: `<`, `>`, `&`, U+2028, U+2029 and invisible format characters (such as a
right-to-left override) are escaped as JSON unicode escapes.

### SARIF

`--sarif` prints the findings as a SARIF 2.1.0 log, the interchange format of code-scanning tools (GitHub
code scanning reads it through its `upload-sarif` action). Each distinct finding id becomes a rule, each
finding a result attached to the analysed file by base name, and the severity maps to the SARIF level:
critical and high are errors, medium is a warning, low and info are notes. Evidence, confidence and
limitations travel in the result's `properties`. Tests cover the structure of the log; it has not been
checked against the official SARIF schema validator or uploaded to a code-scanning service.

```console
$ teardown analyze examples/samples/upx-like.exe --sarif -o app.sarif
```

## strings

```text
teardown strings <file> [flags]
```

| Flag | Meaning |
|---|---|
| `-c, --category LIST` | Only these categories, comma separated: `secret`, `url`, `email`, `ip`, `registry`, `command`, `useragent`, `path`, `domain`, `api`, `base64`, `hex`, `plain` |
| `-n, --min N` | Minimum string length (default 5) |
| `--max N` | Maximum strings to extract (default 20000); classified strings are kept first |
| `--json` | JSON instead of one string per line |
| `-o, --output FILE` | Write to `FILE` |

Secrets (AWS access key IDs, GitHub and Slack tokens, PEM private key headers, JWTs) are never
printed in full: the first four characters and the length are kept.

```console
$ teardown strings dropper.bin --category url,ip,secret,command
0x00000e00 a url       https://update.example.test/gate.php
0x00000e25 a url       http://198.51.100.23:8080/beacon
0x00000e46 a ip        203.0.113.7
0x00000e63 a command   cmd.exe /c whoami /all
0x00000e7a a command   powershell -nop -w hidden -enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQA
0x00000f5e a secret    AKIA…(20 chars)
0x00000f73 a secret    ghp_…(40 chars)
7 of 93 strings shown (minimum length 5, list truncated: raise --max-strings or narrow with --category)
```

(`dropper.bin` is generated by `go run ./examples/gensamples -dropper`; it is a harmless file that
only looks like a dropper to a static scanner.) The column after the offset is the encoding:
`a` for ASCII, `u` for UTF-16LE.

## disasm

```text
teardown disasm <file> [flags]
```

Decodes a window of instructions in Intel syntax with the decoder built into teardown ([code evidence](code-evidence.md)).
The file is read, never executed.

| Flag | Meaning |
|---|---|
| `--at ADDR` | Virtual address to start at, decimal or `0x` hex: an address of the image, as the report shows it. It is mapped through the section table of a PE or Mach-O image or the program headers of an ELF image |
| `--offset OFFSET` | File offset to start at, decimal or `0x` hex. Not together with `--at` |
| `-n, --count N` | Instructions to decode, 1 to 256 (default 24) |
| `--arch ARCH` | `x86` or `x86-64`. Taken from the file header by default; give it for raw bytes (a file that is not a PE, ELF or Mach-O image) or to override the header |
| `--json` | Print the window as a JSON code block of kind `disasm` (the same object as `findings[].code[]`) instead of a listing |

With neither `--at` nor `--offset` the window starts at the entry point, or at the first byte of a file that
has none. A window never runs past the end of the section (or segment) that holds its first byte. Addresses and
offsets are decimal numbers or `0x` followed by hexadecimal digits; signs, underscores and octal forms are
refused, and a file offset is at most the largest signed 64-bit integer.

```console
$ teardown disasm examples/samples/dropper.bin --at 0x1400010e9 -n 6
; dropper.bin: PE, x86-64, section .text, 6 instructions from 0x1400010e9 (file offset 0x4e9)
; Linear sweep: the bytes are decoded one after another, so data can be shown as code and the sweep can lose sync.
; x86 and x86-64 only; bytes that are not understood are shown as db. Not a decompiler: nothing is executed, emulated or resolved.
0x1400010e9  ff 15 b1 10 00 00     call qword ptr [rip+0x10b1]  ; KERNEL32.dll!VirtualAllocEx
0x1400010ef  48 89 44 24 50        mov qword ptr [rsp+0x50], rax
0x1400010f4  48 8b 4c 24 48        mov rcx, qword ptr [rsp+0x48]
0x1400010f9  48 8b 54 24 50        mov rdx, qword ptr [rsp+0x50]
0x1400010fe  4c 8d 05 fb 1e 00 00  lea r8, [rip+0x1efb]  ; 0x140003000 in .data
0x140001105  41 b9 00 02 00 00     mov r9d, 0x200
; more code follows: continue with --at 0x14000110b
```

(`dropper.bin` is generated by `go run ./examples/gensamples -dropper`.) The lines that start with `;` say what
the window is and what it cannot show, the rows are address, bytes and instruction, and the last line says how
to continue. In a PE image a call or a jump through the import table ends with a note that names the import,
the same note the findings and `xrefs` show, and a reference to data names the section it lands in. A listing
over an address that no section holds says where the addresses of the file are:

```console
$ teardown disasm examples/samples/dropper.bin --at 0x1000
teardown disasm: address 0x1000 is not inside any section or segment that holds data in this file; mapped ranges: .text 0x140001000-0x1400011ff, .rdata 0x140002000-0x140002432, .data 0x140003000-0x14000301f, .config 0x140004000-0x1400041c3, .packed 0x140005000-0x140006fff, .rwx 0x140007000-0x1400071ff
```

It exits with status 1. A file that is not a PE, ELF or Mach-O image has no address map, so its rows show file
offsets (the header lines say so) and it needs `--arch`. An ELF, Mach-O or PE file for another instruction set,
ARM64 for example, is refused with a message that says so: only x86 and x86-64 are decoded. It is a linear
sweep: data can be shown as code and the sweep can lose its place, and bytes the decoder does not understand
come out as `db 0xNN`.

## xrefs

```text
teardown xrefs <file> <api> [flags]
teardown xrefs <file> --list [flags]
```

Who calls an import: the places in the executable sections of a PE image (x86-64 or x86) that call an imported
function, with the instructions around each call so the way its arguments are set up is visible. The name is
matched the way the findings match API names: with or without the library (`KERNEL32.dll!VirtualAllocEx` or
`VirtualAllocEx`), in any case, with the ANSI and wide spellings together (`CreateProcess` finds
`CreateProcessA` and `CreateProcessW`).

| Flag | Meaning |
|---|---|
| `--before N` | Instructions to show before each call, 0 to 40 (default 8) |
| `--after N` | Instructions to show after each call, 0 to 20 (default 4) |
| `--max N` | Call sites to show, 1 to 100 (default 10) |
| `--list` | List the imports that have at least one call site, with their counts, instead of the sites of one |
| `--json` | Print the code blocks of the call sites as a JSON array (with `--list`, the imports and their counts) |
| `--color WHEN` | `auto`, `always` or `never` (`NO_COLOR` is honoured) |

```console
$ teardown xrefs examples/samples/dropper.bin VirtualAllocEx --before 3 --after 2
dropper.bin: KERNEL32.dll!VirtualAllocEx
1 call site (PE x86-64, linear sweep of the executable sections)

  #1  call [IAT]  0x1400010e9  (file offset 0x4e9, section .text)
      0x1400010d5  41 b8 00 10 00 00        mov r8d, 0x1000
      0x1400010db  41 b9 00 30 00 00        mov r9d, 0x3000
      0x1400010e1  c7 44 24 20 40 00 00 00  mov dword ptr [rsp+0x20], 0x40
    > 0x1400010e9  ff 15 b1 10 00 00        call qword ptr [rip+0x10b1]  ; KERNEL32.dll!VirtualAllocEx
      0x1400010ef  48 89 44 24 50           mov qword ptr [rsp+0x50], rax
      0x1400010f4  48 8b 4c 24 48           mov rcx, qword ptr [rsp+0x48]

  limits: x86-64 code decoded as a linear sweep (ARM64 and other instruction sets are not
          supported): data inside a code section can be read as instructions, and one wrong byte
          shifts what follows.
  limits: Only calls through the import table and import thunks are found: functions resolved at run
          time are invisible, and packed or protected code hides its real calls.
  limits: A view of the code, not a decompiler, an emulator or a verdict: nothing was executed, and
          the code shows what is called, not why.
```

The heading of each site says how it refers to the import: `call [IAT]` (a call through the import address
table slot, the way compilers call an import), `call thunk` and `jmp thunk` (a call or a jump to a small stub
that itself jumps through the slot, one level), `jmp [IAT]` (a jump through the slot) or `load [IAT]` (any other
instruction that reads the slot). The best sites come first: calls, then calls and jumps through thunks.
`--list` shows which imports are called at all:

```console
$ teardown xrefs examples/samples/dropper.bin --list
dropper.bin
15 of 21 imports have call sites (PE x86-64, linear sweep of the executable sections)

  KERNEL32.dll!ExitProcess         1 call site
  KERNEL32.dll!GetProcAddress      1 call site
  KERNEL32.dll!LoadLibraryA        1 call site
  KERNEL32.dll!VirtualAllocEx      1 call site
  KERNEL32.dll!WriteProcessMemory  1 call site
  KERNEL32.dll!CreateRemoteThread  1 call site
  KERNEL32.dll!OpenProcess         1 call site
  KERNEL32.dll!IsDebuggerPresent   1 call site
  KERNEL32.dll!CreateProcessW      1 call site
  USER32.dll!SetWindowsHookExA     1 call site
  USER32.dll!GetAsyncKeyState      1 call site
  WS2_32.dll!WSAStartup            1 call site
  WS2_32.dll!socket                1 call site
  WS2_32.dll!connect               1 call site
  URLMON.dll!URLDownloadToFileA    1 call site
```

An import that the file has but nothing calls prints `imported, but no call to it was found in the executable
sections: it may be called through a pointer, resolved at run time or hidden by a packer` and exits 0. A name
that matches no import exits 1 and names the imports that are called. The command works on PE images for x86 and
x86-64 only: ELF, Mach-O and other file types are refused with a message that says so (call sites of ELF
images are not implemented yet). When the scan reached one of its [bounds](code-evidence.md#bounds), a note on
stderr says so.

## hexdump

```text
teardown hexdump <file> [flags]
```

A bounded window of the raw bytes of a file, 16 to a row: the file offset, the hex digits and the printable
ASCII characters. Stdout carries only the rows, so it can be piped; a line on stderr says where the window
ended and how to continue.

| Flag | Meaning |
|---|---|
| `--at OFFSET` | File offset to start at, decimal or `0x` hex (default 0) |
| `-n, --length LEN` | Bytes to show, 1 to 4096 (default 128) |
| `--json` | Print the window as a JSON code block of kind `hex` instead of rows |

```console
$ teardown hexdump examples/samples/dropper.bin --at 0x4e0 -n 48
00000004e0  00 c7 44 24 20 40 00 00 00 ff 15 b1 10 00 00 48  |..D$ @.........H|
00000004f0  89 44 24 50 48 8b 4c 24 48 48 8b 54 24 50 4c 8d  |.D$PH.L$HH.T$PL.|
0000000500  05 fb 1e 00 00 41 b9 00 02 00 00 48 c7 44 24 20  |.....A.....H.D$ |
48 bytes shown (file offsets 0x4e0 to 0x50f of 19200); continue with --at 0x510
```

(The offsets are file offsets: the call to `VirtualAllocEx` above starts at `0x4e9`, which is
`ff 15 b1 10 00 00`.) An offset outside the file exits 1, and a length outside 1 to 4096 exits 2. The window
is cut short by the end of the file. With `--json` the section that holds the window (for a PE, ELF or Mach-O
image) is in the block:

```console
$ teardown hexdump examples/samples/dropper.bin --at 0x4e9 -n 6 --json
{
  "kind": "hex",
  "title": "dropper.bin: bytes at file offset 0x4e9",
  "section": ".text",
  "offset": 1257,
  "lines": [
    {
      "offset": 1257,
      "bytes": "ff 15 b1 10 00 00",
      "text": "......"
    }
  ],
  "truncated": true,
  "limitations": [
    "Raw bytes as stored in the file: they show what is there, not what it means. Packed or encrypted data looks like noise."
  ]
}
```

`truncated` is true because more bytes of the file follow the window.

## serve

```text
teardown serve [--addr HOST:PORT] [--max-upload SIZE] [--keep N]
```

| Flag | Default | Meaning |
|---|---|---|
| `--addr` | `127.0.0.1:7777` | Address to listen on; anything but loopback prints a warning |
| `--max-upload` | `256MiB` | Largest accepted upload (`64MiB`, `1GiB`, ...) |
| `--keep` | `50` | Analyses kept in memory; the oldest is dropped first (at most 10000) |

Serves the dashboard at `/` and the JSON API under `/api`. The full reference, the security model
and the limits are in [api/http.md](api/http.md).

## mcp

```text
teardown mcp [--root DIR]...
```

Newline-delimited JSON-RPC on stdin and stdout; logs go to stderr. Files are readable only below
the `--root` directories (default: the current directory). Setup for Claude Desktop and Claude
Code is in the [MCP guide](mcp.md).

## completion

```text
teardown completion <bash|zsh|fish|powershell>
```

| Shell | Install |
|---|---|
| bash | `source <(teardown completion bash)` |
| zsh | `teardown completion zsh > "${fpath[1]}/_teardown"` |
